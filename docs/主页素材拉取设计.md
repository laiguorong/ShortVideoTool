## 4. 技术选型

### 4.1 为什么不新建一条爬取链路（被否方案）

曾考虑写一个独立的 `user_pull_task` + 独立 worker。否决原因：调度、启停、达上限自动停用、执行日志、实时进度、in-flight 取消、阶梯重置——**这些逻辑合计 400+ 行且都已在 `material_service` 里跑通**，复制一份等于制造两个必然漂移的实现。

改为在阶段 A 内按 `conditions.source_mode` 分流，阶段 B 完全共用。

### 4.2 为什么用继承而不是复制浏览器会话代码（被否方案）

曾考虑新建 `BrowserUserPostSession` 并复制 `_ensure_open` / `_scroll_until` / `close`。否决原因：

- 复制约 150 行高风险代码，且这些代码里塞满了对 asyncio loop 冲突 / chromium lock / 浏览器被手动关闭的防御（#P0-11、#fix-browser-closed 等），**复制必然漏掉某一处**
- 同一 profile 目录同时开两个 chromium 会撞 lock，继承天然复用同一个 session 对象

改为 `class BrowserUserPostSession(BrowserSearchSession)`，只覆写 XHR 匹配 + 新增采集方法。**`search_api.py` 保持零改动**。

### 4.3 为什么不需要 DB 迁移

`video_pull_task.conditions_json` 是 TEXT，新增键为 `source_mode` / `homepage_urls` / `homepage_sec_uids`。老任务 JSON 没有 `source_mode`，读取时按 `search` 兜底，行为完全不变。

## 5. 数据模型

```jsonc
// conditions_json 扩展（新增 3 键，均有默认值，老数据零影响）
{
  "source_mode": "user_homepage",      // "search"（缺省）| "user_homepage"
  "homepage_urls": [                   // 用户原始输入行，原样保留供编辑回填
    "https://www.douyin.com/user/MS4wLjABAAAA...",
    "https://v.douyin.com/iRxxxxx/"
  ],
  "homepage_sec_uids": [               // 解析后的 sec_uid 缓存，省每轮重复解析
    "MS4wLjABAAAA..."
  ],
  // 以下沿用现有字段
  "title_regex": "探店|测评",
  "orientation": "vertical",
  "max_count": 100,
  "fetch_bgm": true,
  "filter_subtitle": false,
  "filter_face": false
}
```

`homepage_sec_uids` 与 `homepage_urls` 分离的理由：URL 是用户可编辑的原文，sec_uid 是派生数据。**回填以 `homepage_urls` 为准**，避免用户改了链接但 sec_uid 没跟着变导致爬旧主页。

### 6.1 新增 `backend/app/core/douyin/user_post_api.py`

```python
        """逐个主页：goto → 等首屏 → wheel 滚到底 → 提取 aweme_id，去重保序返回。"""
```

复用到的继承成员：`_ensure_open()`（含 sessionid 校验）、`_scroll_until()` / `_scroll_loop()`（wheel 翻页 + has_more 终止 + 空闲超时）、`get_page()`、`close()`、`_safe_wait_or_raise()` / `_raise_if_browser_closed()`（模块级函数，import 复用）。

主页流程细节：

1. `_ensure_open()`（继承）——启动 chromium + 校验登录态
2. 对每个 sec_uid：
   - `page.goto(f"https://www.douyin.com/user/{sec_uid}", wait_until="load", timeout=30s)`
   - `_captured.clear()`
   - 等首屏 post XHR（`_poll_captured_until`，15s）
   - **DOM 兜底**：超时则抓 `a[href*="/video/"]` 的 href 提取 aweme_id（主页首屏可能走 SSR 不发 XHR）
   - `_scroll_until(target_page=None, idle_timeout=20, max_pages=剩余预算)` —— 复用搜索的滚动逻辑，但 `idle_timeout` 收紧到 20s（主页作品少，等 60s 是浪费）
3. 从所有 body 的 `aweme_list` 提取 `aweme_id`，跨主页去重保序

### 6.2 链接解析 `extract_sec_uid(line) -> str | None`

沿用项目既有分享解析风格（`client.py:165-215`），不另发明规则：

| 输入形态 | 处理 |
|---|---|
| `https://www.douyin.com/user/MS4wLjABAAAA...` | 正则直接取 `MS4w...` |
| `https://www.iesdouyin.com/share/user/MS4w...` | 同上（兼容移动端分享） |
| `https://v.douyin.com/XXXX/` | curl_cffi `allow_redirects=False` 取 Location → 落回上两条规则 |
| 分享文本（含中文描述） | `re.findall(r'https?://[^\s]+')` 抽第一个 URL 再走上面 |
| 裸 sec_uid（`MS4wLjABAAAA...`） | 正则校验前缀后直接返回 |
| 无法识别 | 返回 `None`，**记 warning 跳过该行，不阻断其他行** |

### 6.3 阶段 A 分支（`material_service._run_pull_round`）

在现有 `_run_pull_round` 阶段 A 位置按 `source_mode` 分流：

```
source_mode = conditions.get("source_mode") or "search"

if source_mode == "user_homepage":
    session = BrowserUserPostSession(profile_dir, headless=None)
    aweme_ids = session.collect_homepage_ids(sec_uids, page_budget, progress_cb)
    # 单主页 0 数据 → warning + 继续下一个，不做整轮 30s+45s 重试
else:
    session = BrowserSearchSession(profile_dir, headless=None)
    aweme_ids = session.search_all_for_ids(keyword, conditions, ...)   # 原逻辑不动
```

主页模式**跳过**的部分（搜索专属）：`_apply_filters()` 筛选面板、`_switch_to_video_tab()`、`_derive_search_keyword()`。

阶段 B 调用 `_run_detail_phase(..., page=session.get_page())` 完全复用。

### 6.4 进度文案

现有阶段 A 模板硬编码"搜索阶段："（`material_service.py:80-106`）。主页模式需要自己的文案，否则用户在任务列表看到"搜索阶段"会困惑。新增同风格 helper：

- `_progress_phase_a_home_idle(elapsed)` → `主页采集：正在加载第 i/n 个主页...`
- `_progress_phase_a_home_scrolling(i, n, pages, videos, elapsed)` → `主页采集（第 i/n 个）：已抓到 X 页 / 累计 Y 条`
- `_progress_phase_a_home_done(total, dup, elapsed)` → `主页采集完成：新增候选 Z 个（已入库跳过 Y 个）`

终态 `_progress_terminal` 与阶段 B 模板不变（数据同源）。

### 6.5 已入库预过滤（仅主页模式）

```python
def _filter_existing_aweme_ids(aweme_ids: list[str]) -> tuple[list[str], int]:
    """按 material.source_ref 过滤已入库作品，返回 (新候选, 已入库数)。"""
    # SELECT id FROM material WHERE source_ref IN (...) AND deleted=0
```

**为什么必须有**：主页作品是固定的（一个博主就那些视频），第 2 轮开始扫到的全是老作品。阶段 B 每条详情抓取要 5-10s，不预过滤的话每次调度都在重复抓同一批视频。搜索场景靠阶梯翻页（100→90→80 页）每轮能翻到新内容，不受影响，所以**该优化只挂在主页分支上，不动搜索路径**。

性能注意：`source_ref` IN (...) 分批（每批 500 个），避免 SQLite 变量上限。

## 8. 风险预演

| 风险 | 概率 | 后果 | 对策 |
|---|---|---|---|
| 主页首屏走 SSR 不发 post XHR | 中 | 首屏作品抓不到 | DOM `a[href*="/video/"]` 兜底（§6.1） |
| 主页作品接口风控比搜索严 | 中 | 整轮 0 数据 | 单主页失败只 warning + 跳下一个；整轮全 0 才写 fail_reason |
| 多主页顺序遍历，中途页面被风控弹验证码 | 低 | 后续主页全废 | 每个主页 goto 后校验 `page.url` 是否被重定向到验证页，命中则中止本轮并写 fail_reason |
| 阶梯页数 `compute_round_pages` 语义漂移 | 低 | 误解预算含义 | 主页模式下语义变为"本轮最多滚多少页"，写进代码注释 + 文档 |
| 用户填了 100 个主页链接 | 低 | 单轮跑几小时 | 建议在弹窗加提示"建议不超过 20 个"；`max_pages` 预算耗尽即停止遍历剩余主页并 warning |
